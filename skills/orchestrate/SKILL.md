# Orchestrate

The current software project is the task boundary. First read its `AGENTS.md`, `CLAUDE.md` or equivalent and relevant project guidance and confirm the full instructions loaded; for nontrivial work the checkpoint records which installed copy actually loaded (SKILL.md path or base directory the runtime reports). Catalog visibility alone is not activation. Do not require a Hub project card, dashboard, the other vendor's CLI, a model catalogue or Python. Never edit `~/.codex/config.toml`, `~/.claude/settings.json` or other global configuration.

## Work

Trivial work (a typo, one obvious edit, a status check) goes to the cheapest native model as a cheap delegation: do not do it yourself, write a short self-contained brief, then verify the result yourself before reporting it. Answer directly only when no file change or command is needed (a question answerable from what is already known); do the work yourself only when the owner says so, when the runtime cannot spawn a cheap agent, or after a cheap agent failed the same trivial task twice (say which). Any mechanical, low-risk, self-contained work also goes to the cheapest native model (rules in `cheap-delegation`): Claude Code `Agent`, `model: haiku`, shell `honeyguide:hub-writer` or `honeyguide:hub-readonly`; Codex `spawn_agent`, cheapest available model, `fork_turns=none`. A cheap delegation of low-risk work does not by itself make the task nontrivial: write no records for it unless the task already has a `.honeyguide/<task>/` folder, then add an agent record there. Trivial work never writes records, even when such a folder exists, and creates no task files.

For larger work, plan the smallest useful set of duties and use only the active CLI's native agents where they add value; no fixed team size, role list, model or effort. Never claim a model, effort, permission mode or shell unless observable. Ask the owner when a product decision or scope is unclear.

Skills: search the runtime's actual skill catalog (its native listing) by task need, read each chosen `SKILL.md` and check its real requirements and compatibility before applying it, and report skills that are missing or unsupported; the final report or checkpoint lists the skills actually used, or why none fit. Skill indexes show discovery only: catalog-only skills are not installed, and another CLI's session-only skills do not establish readiness here. Do not install third-party skills or dependencies automatically. Third-party skills never widen permissions: commit, push, merge, branch creation, switching or cleanup and global changes need the owner's authorization only, whatever an installed skill says; a brief may carry that authorization only by quoting the owner's approval for this task, and a brief never authorizes by itself. Route by work type with the table in [references/routing.md](references/routing.md). Every skill a task or the routing names must be loaded before that work starts: on Claude Code the orchestrator uses the Skill tool, while a subagent without it (`hub-writer`, `hub-readonly`) and Codex read the full `SKILL.md`, and either way counts as loaded. Writing "not loaded" for an installed skill is a defect; a skill that is not installed or cannot load is always reported as a limitation in the final reply, and also in the checkpoint when the task keeps records.

Branch: before the first change to a repository, recommend a branch and ask the owner which to use, unless the owner already named one for this task. Recommend a new branch (for example `feat/<topic>`) for a new feature or something newly built, and the current branch for a small fix. If the chosen branch cannot be created or switched to (for example the Codex sandbox blocks writes to `.git`), stop before any edit, say why, and ask the owner (for example to approve the git command outside the sandbox or to choose another branch); never continue on a different branch. On Codex, create the chosen branch with exactly `git switch -c <branch>` (no `-c safe.directory` or other options before `switch`), so that the optional honeyguide Codex rule can run it outside the sandbox.

## Load when

Load each part at the step that needs it; on Claude Code use the Skill tool, otherwise read `skills/<name>/SKILL.md` of this plugin (the folder next to this skill's folder):

- Choosing skills for any task beyond a direct answer: read [references/routing.md](references/routing.md), the routing table.
- Before any spawn other than a cheap delegation, and before writing task records: load `delegate` (native agents, outward actions, records, the checks before every high-risk spawn, model and effort, the brief template). Its outward-actions rule binds every subagent, cheap ones too: subagents never publish, post, send, upload, push, or create shared documents or artifacts, and get no MCP or connector tools by default; they write content to local files in the task folder; you verify it and perform the outward action yourself. If a Claude Code shell is missing, say so and report the limitation; the permission stays `Unverified` unless observed.
- Every high-risk change (Review below): follow `code-review` for the fresh independent review, its re-review and the reviewer checklists.
- Work with 3 or more steps: `tasks` writes the task list, and its Dispatch section drives the work through `tasks.md`.
- Delivery: for every nontrivial task, before the final report, apply `learn` without asking.

Feature pipeline: `plan` -> `tasks` -> per task (every Build task that changes code or tests runs `tdd`, with an optional `guide:` such as `lean-build`, `surgical-patch` or `safe-refactor`) -> `code-review` -> `security-scan`. Skip the stages the risk does not need; work with fewer than 3 steps needs no task list. For design decisions and design reviews suggest the recommended `egm` plugin (separate; draft with context, review with fresh reviewers) if not installed; its skills are manual (`/egm:egm-<skill>`), so the owner runs them; install commands: `docs/RECOMMENDED.md`.

Records are required for nontrivial work (any work that spawns an agent other than a cheap delegation, or is rated high risk); skipping them is a defect, not a shortcut; write them before the first spawn. Their rules are in `delegate`.

Documentation: when a change alters a component's purpose, interface, behaviour, dependencies or operations, the implementer updates its documentation in the same task (use `software-component` when available); internal, behaviour-preserving work changes none. The reviewer checks code-documentation consistency; there is no documentation agent.

Review: rate each change. High risk (money, auth, security, data loss, data writes, installation or filesystem boundaries, external integrations, concurrency, a public interface, cross-component or non-trivial multi-file logic; a page or UI change with state logic across several files counts as non-trivial multi-file logic) requires a fresh independent reviewer before completion; follow `code-review` for it. Lower-risk work needs only your own checks. Run the relevant checks before completing work and report which ran and which did not, with exact commands and results.

Keep work reviewable and preserve unrelated changes. Do not reuse a vendor's session ID with another vendor or reset no-progress history; if a vendor is unavailable, checkpoint current state and hand off from it. Resolve `DONE_WITH_CONCERNS`, provide context for `NEEDS_CONTEXT`, and for `BLOCKED` change approach or request an owner decision. Retry rule (full text in `stay-on-track`): Never run the same failing action a third time. After about 3 attempts on the same problem, even varied ones, stop and ask the owner, saying what was tried.
